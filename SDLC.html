Software Development Lifecycle

AI-native SDLC

These notes summarize the AI-native SDLC playbook published by Claude. The central idea is to redesign the whole lifecycle around agentic AI, rather than only using AI to write code.

A traditional SDLC moves work through planning, design, build, test, deployment, and maintenance using human-owned handoffs, documents, tickets, and approvals. An AI-native SDLC embeds AI in every stage and turns the lifecycle into a feedback loop.

The build phase may become much faster when agents produce code, so the bottleneck moves to planning, review, testing, deployment, and governance. The response is to make those surrounding processes machine-readable, automated where appropriate, and easier for people to supervise.

  • Artifacts replace lossy handoffs: each stage commits an artifact that the next stage can read.
  • AI operates throughout the loop: agents help plan, design, implement, test, review, deploy, and diagnose.
  • People remain accountable: humans make decisions that require judgment and retain approval over important risks.
  • Controls move closer to the action: policies, hooks, permissions, and automated checks guide or block unsafe actions.

The playbook treats the chain of version-controlled artifacts as both the handoff mechanism and the audit trail. The exact names can vary, but the next stage should be able to understand what the previous stage decided.

  • Plan: intent.md captures the problem, outcome, users, constraints, and open questions.
  • Design: spec.md turns accepted intent into requirements and a design, with policy concerns flagged.
  • Build: plan.md names the files, implementation order, risks, and proof required.
  • Test: the diff, tests, evaluations, and feedback show whether the change works.
  • Deploy: the pull request and review findings record what was checked and approved.
  • Maintain: incidents and operational signals can create a new intent.md and restart the loop.

Git history adds authorship, timestamps, revisions, and approvals to the artifact chain. If legacy tools remain authoritative, each artifact should clearly identify its source of truth and link back to the corresponding record or commit.

The originator describes a problem in ordinary language and works with an agent to make the idea concrete. The agent asks about scope, users, constraints, success, and open questions, then records the result in a human-readable and machine-actionable intent.md.

A product owner corrects misunderstandings and decides whether the intent should proceed. The accepted commit triggers the design stage. This reduces the number of handoffs between the original problem and the team that will solve it.

Useful measure: time from the first conversation to a committed intent, plus the proportion of intents accepted into design.

The agent reads the accepted intent and produces a requirements and design specification in one guided session. Organizational standards for security, compliance, UX, architecture, and brand can be encoded as reusable skills or instructions and applied while the specification is written.

The product owner reviews whether the specification still solves the original problem. Flagged concerns are resolved with the relevant policy owners before spec.md is accepted and the build stage begins.

Useful measure: requirements rework after planning begins, especially changes to the specification after the first implementation plan.

Engineers start in plan mode with the intent and specification. The agent inspects the repository, proposes the files and sequence of work, identifies risks, and names the tests that will prove the change. After the engineer accepts plan.md, the agent can implement against it.

Team knowledge belongs in version-controlled files such as CLAUDE.md and reusable skills. Hooks can enforce rules deterministically, such as protecting generated code, scanning for secrets, or running a formatter after edits. Auto-accept and parallel sessions are best reserved for routine work with a small blast radius and strong checks.

Existing systems such as Jira or requirements tools do not need to disappear. Choose one source of truth for each artifact and maintain an explicit link when systems coexist.

An agent that can produce code quickly also needs a fast feedback loop. Give it one-command builds, tests, linting, and measurable acceptance criteria. For UI work, include a browser or screenshot check so visual behavior is verified before human review.

Continuous evaluations extend ordinary tests to agent behavior. A team can collect representative tasks, define acceptable outcomes, run them in CI when prompts or skills change, and turn production incidents into regression cases.

Principle: the session should check its own work and iterate before a person has to inspect the result.

AI can review pull requests in consistent passes for bugs, security, and compliance, while human reviewers focus on intent, risk, and the final decision. Review policies should define severity and keep the agent that made a change from approving it.

Deployment automation should be sandboxed, use scoped credentials, and expose only approved actions. Branch protection, environment-specific permissions, hooks, and named release approvals preserve the production boundary. The agent may prepare or propose a release, but it must not bypass the gate.

Useful measures: time to first review, pre-merge defects and vulnerabilities, deployment frequency, change failure rate, and recovery time.

Maintenance becomes an active feedback loop instead of a queue that waits for someone to restart the process. A deterministic monitor can watch a stable baseline such as test failure rate, post-deploy errors, or service latency. When a control band is breached, the agent diagnoses the evidence and writes the finding as a new intent.

Response tiers can separate logging, read-only diagnosis, and proposals such as a pull request or a pre-approved rollback. Production changes still pass through the normal review and release gates. The same pattern can support recurring security scans and incidents received through team communication tools.

Important boundary: detection should be deterministic; the model is invoked after the signal is detected and is constrained by the response tier.

  • Start with one stage where the current bottleneck and outcome are measurable.
  • Commit artifacts so that people and agents share the same source of context.
  • Encode institutional knowledge in reviewed, version-controlled instructions and skills.
  • Make permissions, hooks, tests, evaluations, and approval gates explicit.
  • Increase autonomy only as the feedback loop becomes reliable and the blast radius is understood.
  • Keep humans above the loop for judgment, accountability, regulated changes, and critical production actions.

The goal is not to remove people from software development. It is to move human attention from repetitive handoffs and line-by-line supervision toward intent, risk, governance, and the decisions that matter most.
