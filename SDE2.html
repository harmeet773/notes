Important Problem: Top K Frequent Elements

Problem: Given an array of integers, return the k most frequent elements.

Key Points
  • Order does not matter
  • Focus on frequency, not value
  • Works with duplicates and negative numbers
Approach 1: Sorting (O(n log n))
  1. Count frequency using HashMap
  2. Convert map → array
  3. Sort by frequency (descending)
  4. Return first k elements

function topKFrequent(nums, k) {
    const freqMap = new Map();

    for (let num of nums) {
        freqMap.set(num, (freqMap.get(num) || 0) + 1);
    }

    const arr = Array.from(freqMap.entries());
    arr.sort((a, b) => b[1] - a[1]);

    return arr.slice(0, k).map(item => item[0]);
}

Time: O(n log n)

Approach 2: Min Heap (O(n log k))
  • Use a min heap of size k
  • Remove smallest frequency when size exceeds k
  • Keeps only top k elements

Time: O(n log k)

Approach 3: Bucket Sort (O(n))
  1. Build frequency map
  2. Create buckets (index = frequency)
  3. Store elements in buckets
  4. Traverse from highest frequency

function topKFrequent(nums, k) {
    const freqMap = new Map();

    for (let num of nums) {
        freqMap.set(num, (freqMap.get(num) || 0) + 1);
    }

    const buckets = Array(nums.length + 1).fill().map(() => []);

    for (let [num, freq] of freqMap.entries()) {
        buckets[freq].push(num);
    }

    const result = [];

    for (let i = buckets.length - 1; i >= 0 && result.length < k; i--) {
        result.push(...buckets[i]);
    }

    return result.slice(0, k);
}

Time: O(n)

Interview Tip
  • Start with sorting (baseline)
  • Optimize using heap
  • Mention bucket sort for best answer

Scalability is the ability of a system to handle increased workload by adding capacity while maintaining acceptable performance.

Vertical scaling (scale up)
  • Add more CPU, memory, storage, or network capacity to an existing server.
  • Advantages: simple to implement, no application-level distribution required, and easier data consistency.
  • Disadvantages: hardware limits, downtime for upgrades, higher cost, and a single-node failure risk.
  • Best for monoliths, small databases, and workloads that are difficult to partition.
Horizontal scaling (scale out)
  • Add more machines and distribute traffic or work across them, usually behind a load balancer.
  • Advantages: higher capacity, fault tolerance, and limited physical scaling ceiling.
  • Disadvantages: more operational complexity, distributed state management, and consistency challenges.
  • Requires the application to be stateless or to manage shared state through stores such as Redis or a database.
  • Best for web tiers, microservices, queues, and workloads that can be partitioned or replicated.
Design considerations
  • Stateless services: Keep session and request state outside application instances.
  • Database bottleneck: Use read replicas, caching, partitioning/sharding, or optimized queries.
  • Availability: Run replicas across failure domains and deploy instances without a single point of failure.
  • Cost and elasticity: Horizontal scaling is often more cost-effective and elastic in cloud environments.
  • Autoscaling: Scale based on metrics such as CPU, memory, queue depth, or request latency.

Common approach: Start with vertical scaling for simplicity, then scale out the bottlenecks that can be distributed. Most production systems combine both forms.

Notes
  • CAP Theorem: Choose between Consistency, Availability, Partition tolerance
  • Caching: Reduces DB load, improves latency
  • Design Tip: Always start with requirements → scale later
Rate limiting controls how many requests a client can make within a given time window.
design approaches

Tokens are added at a steady rate. Each request consumes one token.

class TokenBucket {
  constructor(capacity, refillRate) {
    this.capacity = capacity;
    this.tokens = capacity;
    this.refillRate = refillRate;
    this.lastRefill = Date.now();
  }

  allowRequest() {
    const now = Date.now();
    const elapsedSeconds = (now - this.lastRefill) / 1000;
    this.tokens = Math.min(this.capacity, this.tokens + elapsedSeconds * this.refillRate);
    this.lastRefill = now;

    if (this.tokens < 1) return false;
    this.tokens -= 1;
    return true;
  }
}

Only requests that fall inside the moving time window are counted.

function allowSlidingWindow(requestTimes, now, windowMs, limit) {
  const recentRequests = requestTimes.filter(
    requestTime => now - requestTime < windowMs
  );

  if (recentRequests.length >= limit) return false;
  recentRequests.push(now);
  return true;
}

Requests enter a queue and leave at a fixed processing rate.

class LeakyBucket {
  constructor(capacity, leakRate) {
    this.capacity = capacity;
    this.leakRate = leakRate;
    this.queue = [];
  }

  addRequest(request) {
    if (this.queue.length >= this.capacity) return false;
    this.queue.push(request);
    return true;
  }

  processRequests() {
    return this.queue.splice(0, this.leakRate);
  }
}

Each fixed time interval has its own request counter.

function allowFixedWindow(state, now, windowMs, limit) {
  if (now - state.windowStart >= windowMs) {
    state.windowStart = now;
    state.requestCount = 0;
  }

  if (state.requestCount >= limit) return false;
  state.requestCount += 1;
  return true;
}

Design patterns are reusable solutions to recurring software design problems. They should describe intent and improve the structure of code, not merely add abstractions.

Adapter Pattern

An adapter converts one interface into another interface that a client expects. It is useful for integrating third-party libraries, legacy code, APIs, databases, and file formats without changing either side's implementation.

// Client interface
interface UserService {
  getUser(id: string): User;
}

// Adapter
class PaymentUserAdapter implements UserService {
  constructor(private paymentLibrary: PaymentLibrary) {}

  getUser(id: string): User {
    const customer = this.paymentLibrary.fetchCustomer(id);

    return {
      id: customer.userId,
      name: customer.customerName
    };
  }
}
  • Purpose: bridge incompatible interfaces.
  • Use when: the client and dependency can work together but expose different contracts.
  • Avoid when: you can change one side directly, or the mapping is simple and the adapter only adds indirection.
Other Related Patterns
  • Factory Method: lets subclasses decide which object type to create while keeping object creation in a common workflow. Learn Factory Method
  • Decorator: adds behavior to an object dynamically while preserving its interface.
  • Proxy: provides a controlled replacement for another object, often for access control, caching, lazy loading, or remote calls.

Practice: identify the problem each pattern solves, then compare its structure and trade-offs with composition, inheritance, dependency injection, and direct implementation.
